Pico 2 SRAM monitor functional specification
============================================

Purpose and design policy
-------------------------

The project gives students a short edit/build/upload/run cycle for assembly programs on real hardware. It approximates a minimal Linux userspace where that makes experiments familiar: static ELF loading, an exec-style stack, Linux syscall numbers, console descriptors, and a brk heap. Programs must link to physical SRAM and accept the documented syscall subset. Running arbitrary Linux applications, hosting a filesystem, or providing process isolation between multiple guests is outside the current scope.

The guest is strictly isolated from the monitor and the rest of the system. Inside its sandbox, protection is opportunistic debugging assistance. Accept a layout requiring RWX access when it can be isolated. Never remove a permission required by an ELF segment to make another segment safer. The primary internal risks are student pointer, indexing, stack, and allocation mistakes. A fault is useful evidence; lack of a fault is not evidence that an access was correct.

`EXECUTABLES.md` is the executable and shell contract. `DESIGN.md` records decision rationale and validation milestones. All source and build rules are in this directory; dependency trees are subdirectories. Git remains read-only unless explicitly authorized otherwise.


Hardware and trusted memory
---------------------------

RP2350 runs one guest with up to two U-mode threads, without an MMU. Each thread slot is pinned to its corresponding hart. Both harts can enter one serialized M-mode monitor. Pico 2 has 520 KiB SRAM: 512 KiB main SRAM followed by two 4 KiB banks. The board used for earlier hardware validation is revision A2, chip ID 081212E1C341B500, with 4 MiB flash.

The flash-executing monitor reserves 16 KiB at 0x2007c000..0x20080000 for static storage, leaving 496 KiB of main SRAM for the guest arena. Its static allocation extent and measured normal-stack use are reported by `map`. Linker region limits enforce the main reservation. No heap allocator is linked; the SDK minimum heap allowance is 256 bytes. Static storage occupies 15144 bytes: 3852 initialized bytes, 11240 BSS bytes, and 52 bytes of inter-section alignment. With the heap allowance, 984 bytes remain inside the reservation.

Both the protected monitor and monitor_emu execute from flash and use the same SRAM layout; SRAM-executing firmware and its startup diagnostic are unsupported. CMake rejects PICO_NO_FLASH. The guest floor and recommended executable base are always 0x20000000; valid higher ELF destinations remain supported. GUEST_END in memory.h and RAM_ORIGIN in monitor.ld must agree.

Guest allocation ends at the monitor's lower boundary. Protected snapshots occupy its upper end and bound the runtime sandbox. Scratch bank X at 0x20080000..0x20081000 holds only the 4096 output payload bytes in a NOLOAD section. Its indices begin empty in BSS, so payload bytes require no initialization or flash image storage. Scratch bank Y at 0x20081000..0x20082000 holds the one shared normal stack. Linker assertions enforce both bank assignments. Guest frames, pending calls, the atomic gate and panic words, and IRQ vector table remain ordinary main-SRAM static allocations. There are no saved C continuations, private normal stacks per core, or permanent emergency stacks.

Normal-stack reservation is 4 KiB. Compiler-assisted conservative accounting identifies a 1536-byte service chain after frame-codec compaction, leaving 2560 bytes above that chain. Measurements are evidence for budgeting, not proof of all-path bounds. Monitor growth can change guest capacity without changing its stable link address.

RP2350 has eight configurable PMP entries supporting OFF and NAPOT, minimum region 32 bytes. Lower entry numbers win. Hardwired entries after them grant access to ROM/peripherals, so configurable entry 7 always denies the entire address space using address pattern 0x3fffffff. RP2350-E6 transposes R and X relative to standard RISC-V; hardware writes translate permissions through SDK register definitions. PMP locks remain clear and PMPCFGM0=0 so M-mode can initialize guest memory.

ACCESSCTRL additionally removes unprivileged access to ROM/XIP and peripherals. Writes require the 0xacce0000 key, including read/modify/write operations. Shared SRAM-bank NSU access remains enabled; PMP selects guest addresses. No DMA, device, ROM service, or peripheral register is delegated to the guest. mtval is hardwired to zero and cannot identify fault addresses.

References: [RP2350 datasheet](https://datasheets.raspberrypi.com/rp2350/rp2350-datasheet.pdf), Pico SDK 2.3.1, and TinyUSB commit 86ad6e56c1700e85f1c5678607a762cfe3aa2f47. Dependency setup pins local toolchain and build dependencies. SDK upgrades require auditing vector layout and register behavior.


Boot, service, and trap transaction
----------------------------------

SDK startup initializes clocks, flash/XIP, static storage, and the normal stack. main disables global interrupts, paints unused stack below its live frame for measurement, checks watchdog reboot state, enables watchdog recovery, installs trusted trap vectors, disables inherited peripheral IRQs, initializes deny-all PMP and ACCESSCTRL, forgets guest state, configures the 1 MHz timer, initializes USB, and enables USB plus MTIP interrupt sources.

Boot sets the trusted gate word to owned, marks both cores as expected panic participants before beginning the ROM FIFO launch handshake, launches hart 1 with a stack-free assembly entry, and abandons hart 0's C continuation through monitor_start_locked. Before launch begins, only hart 0 is a participant. A panic during the handshake conservatively waits for hart 1 or watchdog recovery. Hart 1 waits at the gate without touching the shared stack. After bootstrap, each monitor invocation results from a trap. The gate uses one atomic SRAM word, acquired with amoswap.w.aq and released with amoswap.w.rl; it does not use the SDK spinlock abstraction or a hardware spinlock number.

Interrupts stay disabled while waiting for or holding the gate. Its owner establishes fresh sp/gp/tp and enters monitor_dispatch. An invocation services local IRQs/timer, pumps TinyUSB/input/output, advances upload/loader jobs and both threads' pending calls, emits shell/map output, and updates the watchdog. It returns either its own runnable thread's frame or a park disposition; it never blocks or retains a C continuation.

Before guest entry, install the verified PMP plan locally, mark the thread executing under the gate, and select its trusted frame. Assembly abandons the C stack, releases the gate, sets mscratch to the frame, restores registers, sets MPP=U/MPIE=1 with kernel-selected TW, fences instruction fetch locally, and executes mret. Counter access stays disabled. On trap, assembly saves x1..x31 and PC/cause/status through mscratch without trusting guest sp/gp/tp, clears mscratch, and acquires the gate. Only the owning core clears its thread's executing flag and publishes its saved trap. Other cores never inspect a frame still owned by an executing core. Interrupts leave PC unchanged; a dispatched ecall advances PC four bytes exactly once. A breakpoint trap consumes its two-byte c.ebreak or four-byte ebreak immediately and requests the same two-thread suspension barrier as keyboard suspension. Breakpoints arriving during the barrier are also consumed; resume preserves registers and pending calls and continues after each breakpoint.

On park, assembly abandons the C stack, releases the gate, clears mscratch, and mret enters an M-mode WFI loop with interrupts enabled. A local timer or device interrupt reenters the stack-free gate without saving an idle machine context. Periodic per-core deadlines guarantee progress when another invocation makes a blocked thread runnable; correctness needs no courtesy interrupt.

An M-mode synchronous exception begins stack-free panic coordination. Assembly clears mscratch and interrupt enables, captures PC/cause in registers, and installs a direct stack-free halt vector for nested exceptions. An LR/SC election publishes owner 1 or 2 for hart 0 or 1; the loser parks instead of overwriting ownership or diagnostics. Guest trap entry checks for panic after preserving its scratch registers. Gate entry, every gate-spin iteration, the owned entry, and the C return boundary also check, so a peer can abandon a held gate or completed activation without acquiring or releasing the normal lock. A request racing past the final check may allow another guest interval, but the owner cannot reclaim RAM until the peer subsequently traps and acknowledges.

The peer disables interrupts, clears mscratch, installs the halt vector, and atomically ORs its bit into the parked mask with release ordering. After acknowledgment it only executes the stack-free halt loop; no C continuation or guest frame is restored. The owner waits with acquire ordering for all expected peers, leaving SP untouched and making no writes to guest RAM. No acknowledgment means watchdog recovery rather than an unsafe stack claim. When all peers are parked, the owner sets sp to 0x20001000, restores trusted gp/tp, and calls monitor_kernel_fault on the disposable first 4 KiB of guest SRAM. Only the owner records PC/cause in watchdog scratch registers and requests BOOTSEL through the existing C/ROM path. The normal gate can remain held throughout recovery. Nested faults and unexpected recovery returns halt without republishing acknowledgment or diagnostics. Watchdog expiry also returns to BOOTSEL. Software bootsel uses the ROM reboot API.

The vector table preserves the SDK handler-table layout at VTABLE_FIRST_IRQ. Hardware slots are uncompressed four-byte jumps; monitor_vectors contains the copied SDK table. Xh3irq dispatch uses MEINEXT and MEICONTEXT, with bounded attempts and no nested M-mode interrupts. Unexpected persistent IRQs are masked and reported. The ordinary protected build uses MTIP, not the external timer alias as a second source.

U-mode is preempted on locally delivered USB/timer events, with timer deadlines normally rearmed at most 1 ms ahead. Interrupt service waits until the receiving core owns the gate; no forwarding is needed. File clearing, snapshot copies, reset clearing, and brk growth are chunked to at most 1024 bytes. Console completion moves at most 256 bytes. ELF planning retains explicit traversal state: a solve step evaluates at most 512 cells/candidate combinations, reconstruction advances one transition per invocation, and independent verification checks 4096 address bytes per invocation. No guest executes during loading.


USB, console, and transport transaction
---------------------------------------

The host utility is one executable Python standard-library script, src/pico.py, copied to dist/pico. `pico FILE` validates the ELF locally, opens the console, sends Ctrl-C to interrupt any guest or partial command, waits for the prompt, issues load, waits for upload readiness, and transfers the image through the upload CDC interface while draining console output. It then keeps the same console open for interactive commands; the guest remains READY until run. `pico` opens only the console. `pico --send FILE` uploads to a session already armed by load in another console, including load --no-reset. Stable interface identities are discovered separately; --console-port and --upload-port provide explicit device paths. Interactive sessions restore terminal settings and close the console on success, failure, SIGTERM, or interruption. Tests import the same module for framing and serial helpers and exercise the CLI through terminal PTYs against the emulator. The detach sequence retains its pico-console identifier as a wire protocol value.

Combined upload/console mode displays the monitor's load summary without a separate host success line. Upload-only `--send` mode prints the uploader result; upload failures remain errors in both modes.

Two CDC ACM interfaces share one USB cable. Console CDC carries shell and guest input/output; upload CDC carries framed ELF transfer. TinyUSB is called directly without pico_stdio_usb, its background worker, or its reset interface. USB IRQ 14 queues work; foreground tud_task_ext(0,false) performs bounded work while global IRQ delivery remains masked.

Buffers are fixed: 512 bytes per CDC RX/TX FIFO, a 512-byte guest input ring, a 4 KiB ordered output ring with 2 KiB held back for diagnostics, a 1056-byte encoded receive buffer, a 192-byte encoded reply buffer, 1024-byte DATA payloads, and a 4096-byte ELF prefix. Transport buffers remain monitor-owned so a complete first DATA frame can be validated before invalidation. Loader prefix and 1024-byte upload buffers live in guest SRAM. No guest pointer reaches TinyUSB. Short endpoint writes preserve order; USB backpressure permits frames larger than a FIFO to arrive incrementally. Disconnection suspends guest execution, cancels uploads, and discards undeliverable console output with counters.

Shell input uses a 2304-character command buffer. Single/double quoting and backslash escaping are literal syntax; no expansion or command execution exists. help lists command usage, and help COMMAND describes an individual command. Ctrl-C and Escape suspend active guests before ordinary input buffering, even when the guest input ring is full. Suspension and resume clear queued keyboard input. Resume returns to ACTIVE with the preserved thread states, pending syscalls, PCs, and registers. run starts READY guests and automatically resets EXITED guests when reset support is retained, preserving the parsed arguments until the incremental reset completes. Suspended and faulted guests require explicit reset before a fresh run; reset prepares READY but does not run automatically. Console disconnection cancels a queued run. The shell quit command emits a detach sequence consumed by pico-console; Ctrl-D at the monitor requests detachment; Ctrl-] detaches in the host client. Console reconnection reprints the banner and prompt. Map output emits a bounded section or range row per service pass only when at least 512 output bytes are free, and delays the prompt until complete. An eight-byte stage/cursor record drives address-ordered traversal without a stored interval list. Rows split at exact ELF endpoints, heap base/break/limit, stack boundaries, snapshot/monitor boundaries, and every PMP region endpoint. Overlapping ELF requirements are unioned; effective access and the winning entry use first-match priority. Labels distinguish ELF, used heap, mapped heap capacity, stack guard, stack, reset reserve, unused memory, and monitor storage. Exclusive end addresses and the required/effective distinction are explained before the table. The following PMP plan lists all seven optional entries (unused entries OFF) and the system-deny entry, with NAPOT pmpaddr values; it describes installation on guest entry rather than live register readback. Reset accounting and monitor memory measurements follow. Both info and map print each ELF read/write/execute permission independently.

load arms a timed upload session. The host receives READY and sends BEGIN containing length, expected whole-file CRC, and bounded name. DATA carries session/sequence/offset/payload and frame integrity. The monitor accepts only expected stream positions; identical retransmitted DATA is acknowledged without copying or updating CRC twice. END verifies total length and whole-file CRC, waits for loader jobs, then publishes a final RESULT. Duplicate END replays that result. Invalid framing, timeouts, disconnect, cancellation, and capacity failures have explicit outcomes. Host framing uses COBS and CRC; limits remain 1 MiB file and 1024-byte payload.

COBS decode compacts the receive buffer in place, then validates version, type, length, and CRC before exposing a borrowed payload view. That view expires when the buffer is reused; loader_feed copies accepted data into its own guest-resident upload buffer before returning. Encoding consumes a borrowed payload synchronously and streams header, payload, and CRC into the bounded output without a full raw-packet stack array. Replies contain at most 162 payload bytes; the final RESULT remains encoded in the reply buffer for duplicate END/ABORT requests until another upload is armed. Transfer state occupies 1360 bytes plus a four-byte session generation counter.


ELF planning and replacement transaction
---------------------------------------

Before the first accepted nonempty DATA payload is stored, revoke PMP and forget the old program, including pending reset/syscall work. Arming, BEGIN, cancellation, and timeout before that payload preserve the old program. Buffer min(file size,4096) bytes and validate little-endian System V ELF32, RISC-V ET_EXEC, soft-float ILP32 flags, standard header sizes, entry alignment, bounded ranges, and segment alignment. Headers must fit in that prefix and number at most sixteen. Accept file sizes from 52 bytes through 1 MiB. Section headers, symbols, and debug information do not affect placement.

PT_LOAD destinations use p_vaddr. p_paddr does not request another copy. Multiple R/RX/RW/RWX segments, arbitrary ordering, shared file sources, and BSS-only segments are supported. Write-only ELF requests receive RW access because the hardware requires R with W. GNU_STACK is optional; when present it must request non-executable RW and no more than the default 16 KiB stack. Dynamic/interpreter/TLS program headers are unsupported. Known passive attributes, notes, PHDR, GNU_RELRO, and GNU_PROPERTY metadata need no runtime operation here.

Initialized destination overlaps are accepted only when they reference identical source offsets. Required permissions are unioned across all memory overlaps and across 32-byte hardware granules. A valid entry lies within initialized executable content. Every load destination must fit the guest arena.

memory_plan_start/memory_plan_step compute image end, heap start aligned to 32 bytes, initial stack and snapshot placement, and optional guard space. memory_plan_build is a synchronous adapter for native checks. The initial stack is 16 KiB; no second stack is reserved. A 1 KiB logical gap below it is reserved when enough space remains; hardware denial of that gap is optional. Heap capacity spans from image end to that gap. Unused holes below image end do not become separately allocatable heaps.

Reset support is chosen once during header processing. `load` requests automatic retention; `load --no-reset` skips it. Prefer a stack-sized (16 KiB) aligned snapshot boundary to reduce PMP cost, then try a compact 32-byte boundary if fitting/headroom requires it. Automatic retention requires at least 32 KiB of heap capacity with snapshots and a verified PMP layout; otherwise loading falls back to no reset support. Explicit no-reset avoids snapshot storage. Snapshot payload is the sum of initialized writable segment sizes, packed in segment order; duplicate writable overlaps can occupy duplicate snapshot bytes. Reserved storage includes alignment padding.

The solver uses fifteen workspace levels in disposable guest SRAM beginning 8192 bytes above GUEST_BASE. Initial prefix and upload buffers occupy the first 5120 bytes, separately from this workspace. Planning only runs during loading, before any segment destination is written. The solver builds a NAPOT tree rooted at main SRAM. Each 32-byte cell has required permissions, trusted ownership, and debugging roles. Dynamic programming considers inherited permissions, optional region overrides, and left/right budget splits. Uniform subtrees terminate directly. Child exceptions are emitted before enclosing fallback grants. Permission candidates are NONE, R, RX, RW, RWX; granting extra access inside the sandbox is allowed. Explicit candidate counters preserve inherited-permission, budget, selected-permission, and left-budget order across bounded steps. Each choice retains its selected permission and left budget separately; Choice remains 16 bytes and each workspace level remains 1312 bytes.

The lexicographic score counts, in order: denied cells in the nearest 1 KiB below the stack; text bytes without W; read-only-data bytes without W; writable bytes without X; unused bytes denied. Equal scores prefer fewer entries. This is a deterministic best effort within the supported tree and placement candidates, not a claim of globally optimal placement over every SRAM address.

A PMP boundary cannot split adjacent executable granules: a four-byte instruction can begin two bytes before that boundary, and Hazard3 rejects a fetch spanning different first-match entries even if both grant X. Candidate region boundaries inside continuous executable requirements are therefore forbidden. This can sacrifice partial text protection to preserve execution. The hardware RWX fixture exercises such a two-byte-aligned instruction.

An independent verifier checks entry geometry/configurations, runtime range ordering, required permission coverage, executable-entry continuity, and trusted denial throughout all 512 KiB of main SRAM, including monitor memory above GUEST_END. It does not trust DP scores. Only a verified complete plan permits writing segment destinations. Header or planning failure after the first payload leaves EMPTY. LOAD_PLAN is busy work: the transport withholds acknowledgment of the boundary DATA frame until planning and prefix replay finish, retaining both the prefix and that frame's remaining bytes.

After validation and planning, move the contiguous prefix/upload buffer block with memmove into the final stack base. The planning workspace is dead; all segment destinations end below that stack. Replay the prefix through segment/file intersections and consume any remainder of the boundary chunk, then stream subsequent chunks through the same function. Source bytes remain outside every segment destination, including when one source initializes multiple segments. Verify all segment byte counts and whole-file integrity. Clear the entire guest arena in bounded chunks except the union of initialized destination intervals; initialized overlaps win over BSS. This erases planning workspace, both initial and relocated buffers, holes, stack, heap, and snapshot storage before copying initialized writable bytes into the protected snapshot region. Fence instruction fetch, install the committed image, and mark READY only after all work completes. Failure after invalidation leaves EMPTY. Success prints one line with image name, file bytes, heap capacity and stack size in KiB, and reset availability; it never starts map output.


Launch and syscall transaction
------------------------------

No environment settings or storage exist. run accepts at most 31 additional arguments (32 including image name). Argument strings including NULs must fit 2048 bytes. Invalid launch requests retain READY and do not modify guest memory. envp always points to a single NULL pointer on the guest stack; a2 points to that empty table.

At launch, calculate storage first, then place argument strings and tables at the top of the guest stack. Initial sp is aligned to 16 bytes. Tables contain argc, argv including uploaded name as argv[0], NULL, envp, NULL, and auxiliary-vector pairs ending AT_NULL/0. Include AT_PAGESZ=4096 and AT_ENTRY; include PHDR/PHENT/PHNUM only when those headers are mapped. Set convenience a0/a1/a2 values, mark ACTIVE, and clear stale input. Supplied startup derives parameters from sp, initializes gp without relaxation, calls main, and exits.

Linux generic syscall numbers replace the old private ABI; all old guests must be rebuilt. read(63) accepts fd0; write(64) accepts fd1/2. Counts above INT32_MAX return -EINVAL, invalid descriptors -EBADF, and invalid pointers -EFAULT. Zero length does not dereference its pointer. Guest writes expand LF to CRLF. Guest input echoes and edits the current line with Backspace or Delete; CR completes a line as LF, and reads return up to one completed line, including its newline. Ctrl-D submits unfinished input without a newline, or completes a read with zero bytes at the start of a line. Input beyond the bounded ring is dropped. Reads may be short; writes remain pending until every requested byte is queued, advancing in bounded chunks under output backpressure. Completion does not wait for USB delivery. Blocking calls retain arguments as data in PendingCall, never as suspended C frames. Polling resumes the saved guest with the completion in a0.

thread_create(1000) accepts a start PC in a0 and a passthrough parameter in a1. It selects the other core's vacant slot or returns -EAGAIN (-11). Odd, out-of-sandbox, logically unallocated, or effectively non-executable entry addresses return -EFAULT (-14). The new frame is zeroed except PC and x10/a0; sp/gp/tp/ra are zero. The guest owns stack/TLS allocation and entry/return conventions. Success returns the new slot, 0 or 1. There is no join state or per-thread exit record.

exit(93) releases only the caller's slot; the survivor may create a replacement, including in slot 0 after the initial thread exits. The last thread's status becomes the program exit status. exit_group(94) stops both threads and uses its caller's status. Nonzero final status is printed. A synchronous guest fault stops both threads, identifies its slot, and preserves both saved frames for info. sched_yield(124) completes successfully; threads remain pinned rather than migrating or time-sharing their cores. Unsupported numbers return -ENOSYS.

Program lifecycle states are EMPTY, READY, ACTIVE, STOPPED, EXITED, FAULTED, and STOPPING. Threads are unused, runnable, or blocked; each also records whether its core is outside the gate restoring/executing/saving guest state. ACTIVE permits execution and pending-call progress. Status output derives running when either thread is runnable and waiting otherwise; neither distinction nor a pre-suspension lifecycle state is stored separately. Suspension records STOPPING with target STOPPED, closes both guest return paths, and freezes pending operations. The prompt appears only after both executing flags clear; terminal input is ignored during the handshake. Resume retains both contexts and pending calls, including an undispatched syscall trapped during suspension. Fault and group exit use the same acknowledgment barrier with targets FAULTED or EXITED and discard pending calls. Faulted programs cannot resume.

Pending calls carry monotonically increasing request order. Either core can advance either thread's pending call under the gate, place completion in its saved a0, and make it runnable. Reads consume input in request order; writes may interleave at bounded service boundaries. The owning core later resumes the thread on its own return path.

brk(214) returns the resulting break, with zero as a query and failure returning the unchanged value. Valid changes remain between heap base and planned limit and complete in request order. Only the oldest pending heap change advances. Shrink completes in its next service pass; growth clears newly exposed bytes in bounded chunks before publishing the break and returning. A stopped pending growth resumes from its saved cursor; reset discards it. PMP maps heap capacity, not each allocation, so direct guest access can exceed the logical break. Pending calls use a kind-tagged union: console copies retain address, remaining count, and written count; sleep retains a deadline; heap changes retain target, clearing cursor, and a started flag. The heap cursor captures the published break only when the ordered request first advances. Each pending console-copy chunk rechecks logical heap bounds and effective permissions before dereferencing its retained address. Shrinking a pending buffer can cause -EFAULT after an earlier output prefix was queued.

clock_gettime64(403) supports CLOCK_MONOTONIC=1 and writes two signed 64-bit seconds/nanoseconds fields. clock_nanosleep_time64(407) supports that clock with relative flags=0; it validates and copies a 16-byte request before retaining an absolute microsecond deadline. Seconds and nanoseconds must be nonnegative, nanoseconds less than one billion, and arithmetic must not overflow. Nanoseconds round upward to microseconds. Remaining-time storage is unused because there is no signal interruption. The guest helper library exposes millisecond sleep/uptime using these calls.

Every kernel guest copy validates effective PMP read/write permissions and trusted/heap bounds first. Requests can cross adjacent accessible regions. Checked range arithmetic rejects wraparound. All physical accesses remain within validated intervals; M-mode's bypass of unlocked PMP is never used as pointer validation.


Reset transaction
-----------------

Reset requires support retained at load time; otherwise the shell reports that reload is required. It revokes PMP, discards pending syscalls/input, and scans guest SRAM in 1024-byte jobs. Initialized writable bytes are restored from their protected snapshots. Immutable image memory remains intact. Other writable zero-fill and transient storage is cleared; initialized overlaps always win over zero-fill. Protected snapshot bytes are not touched during restoration.

After reset, clear both thread records and status/accounting, reset slot 0's PC and initial sp, reset the break to heap base, mark READY, and prompt. Argument tables are rebuilt at the next run. The memory/PMP plan and snapshot reservation never change during reset, and no planning workspace is needed. Immutable memory that had writable fallback permissions can have been corrupted by guest code; reset is not a complete immutable-image reload.


Build and validation
--------------------

`VERSION` names the release version. `make release` packages `dist/monitor.uf2`, executable `dist/pico`, and `dist/README.md` (copied from `RELEASE.md`) into `dist/pico2monitor-VERSION.tar.gz`, with those three files at its root. The release quickstart is separate from the development README.

On every push, `.github/workflows/release.yml` checks for remote tag `vVERSION`; an existing tag ends release work. Missing tags trigger a build, full `make check`, and `make release`. Publication is serialized across branches. A draft targets the triggering commit; the archive and three individual files upload before publication creates the tag. Failed uploads leave an untagged draft. A rerun for the same commit replaces draft assets and retries publication; a draft for another commit fails explicitly for manual resolution. The workflow needs contents write permission. Local Git operations remain read-only.

make uses ecosystem CMake/SDK dependency tracking; no clean rebuild is needed for normal development. Firmware and host source live in src/, repeatable fixtures and checks in tests/, and dependency setup in scripts/. CMake tracks firmware source and headers; the root Makefile drives builds, tests, packaging into dist/, and dependency downloads into disposable deps/. -fstack-usage emits compiler reports for firmware and SDK C paths. Stack painting begins in main below live frames and does not measure prior startup. The 4 KiB reservation retains margin above measured paths and compiler-assisted call-chain accounting.

Current single-activation stack analysis identifies monitor_dispatch (32 bytes) -> io_service (304) -> shell_input (176) -> transfer_cancel (32) -> result (240) -> console_printf (448) -> _vsnprintf (112) -> _ntoa_long_long (144) -> _ntoa_format (48) as the deepest audited normal call chain: a conservative 1536 bytes in the protected flash build. wire_encode uses a 32-byte frame and wire_decode uses none. Trap entry, gate waiting, guest restoration, and WFI add no stack frames; dispatch starts at __StackTop with interrupts globally disabled, and synchronous monitor faults coordinate stack-free before reclaiming guest SRAM for recovery. Explicit planner state replaces recursive traversal. Service phases return before the next phase begins, so their stack requirements do not accumulate. Boot initialization precedes the fresh dispatch stack and must be considered separately; compiler reports do not bound opaque ROM calls.

Before frame-codec compaction, emulator SP sampling observed a 2304-byte chain while stack painting reported 2296 bytes, demonstrating that painting can miss reserved but unwritten bytes. Historical artifacts are build/stack-analysis.txt, build/stack-emulator-measurements.log, and build/stack-sp-emulator.log. Current compiler-assisted accounting is in build/16k-stack-analysis.txt; the configured shared stack is 4 KiB at 0x20081000..0x20082000. Emulator evidence and conservative call-chain sums do not prove bounds over every SDK/ROM path.

Both monitor targets disable SDK floating-point and exponential printf formatting; console formats use integers, strings, and characters, including 64-bit integer accounting. Double arithmetic helpers are absent from the linked images; 64-bit integer division/remainder helpers remain in flash. SDK linker include overrides collect ordinary compiler text into flash and allocate the output payload in NOLOAD scratch storage; SDK time-critical code remains in RAM. CMake explicitly tracks both include files as link dependencies. The protected build's main-SRAM static extent is 15144 bytes, and its size-tool text total is 48296 bytes (including RAM-resident code and initialized content).

make panic-check builds a dedicated host emulator driver and runs ten production panic-path scenarios against build/monitor_emu.elf and its HEX image. The driver boots both cores through ROM and controls their instruction ordering to test either owner, simultaneous faults in both scheduling orders, an existing gate waiter, completion of an active C invocation, a guest timer trap, pre-launch participation, an unresponsive peer, and nested faults on owner or peer. It supplies invalid interrupted SP/GP/TP, checks guest RAM remains untouched until acknowledgment, checks owner PC/cause reach watchdog scratch registers, and verifies recovery leaves scratch banks unchanged after the peer's normal activation completes. The normal shared stack address comes from the linked ELF. It stops at entry to monitor_bootsel; actual watchdog expiry and ROM BOOTSEL reboot require hardware validation. make check includes panic-check after ordinary emulator integration.

make check orders C formatting, Ruff formatting/lint, and uv run ty check before native sanitizer tests, host framing tests, and emulator integration. The native suite includes a four-cell exhaustive ordered-region oracle against DP scores, malformed ELF/range cases, prefix-backed tiny RWX loading, brk logical bounds and zeroing, launch pointers/alignment, load-time reset policy, framing/retries, and replacement failures. Thread checks cover zeroed entry registers, slot exhaustion and reuse from the survivor, ordered heap changes and reads, suspension acknowledgments, pending-buffer invalidation, group exit, and fault preservation. Guest targets depend on Makefile so changes to link flags rebuild every fixture.

The emulator uses rp2350js's transpiled C release and real USB controller model with two PTYs. It lacks PMP/U-mode/MTIP behavior, so monitor_emu runs guests in M-mode, accepts M ecalls, and uses each core's external timer alias. Its explicit banner prevents confusion with isolation tests. Both cores boot through the ROM launch path. The host adapter accepts flash firmware only. The shared secondary-thread fixture threads_fault now exercises consecutive four-byte ebreak and two-byte c.ebreak suspensions followed by group exit; native tests retain synchronous fault coverage because the upstream decoder aborts rather than trapping on some illegal encodings. Existing upstream generated-header warnings remain visible. rp2350js-c.patch fixes an ORC.B mask defect, checked by dependency setup and startup vectors. Reduced compiler features avoid incomplete emulator Zcmp decoding. Emulator results establish workflows, not sandbox safety.
